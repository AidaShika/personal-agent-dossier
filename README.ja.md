# personal-agent-dossier

[![CI](https://github.com/AidaShika/personal-agent-dossier/actions/workflows/ci.yml/badge.svg)](https://github.com/AidaShika/personal-agent-dossier/actions/workflows/ci.yml)

[English](README.md) | [简体中文](README.zh-CN.md) | **日本語** | [한국어](README.ko.md)

> プラットフォームを乗り換えるとき、パーソナル AI エージェントの「仕事」をそのまま持ち出すための形式です。

## 解きたい問題

AI エージェントのプラットフォームは次々に現れ、乗り換える人も少なくありません。新しいプラットフォームを試すこと自体は簡単です。難しいのは、エージェントを移すことです。

数か月使ってきたパーソナルエージェントは、単なるプロンプトではありません。担当業務と「やらないこと」、定期タスク、長期記憶、ほかのエージェントへの依存、利用するスキルを持っています。これらは通常、乗り換え前のプラットフォームの中に閉じています。手作業で写すと、定期タスクの時刻は残ってもプロンプト全文が欠ける、記憶が種別なしの塊になる、といった欠落が起き、何が失われたかはエージェントの振る舞いがおかしくなるまで分かりません。

**personal-agent-dossier** は、この引き継ぎを 1 つのファイルにまとめるための形式です。機械が検証できる YAML front matter と、人が読める Markdown 本文の組み合わせで、同じ内容を Notion ページとして保存することもできます。このリポジトリ自体も 1 つのスキルとして構成されています。エージェントはクローンして `SKILL.md` を読めば、手順どおりに書き出しと読み込みが可能です。

## ドシエの中身

| 部分 | 内容 |
|---|---|
| 役割（role） | 担当業務の全文（原文のまま）と「やらないこと」 |
| 定期タスク（routines） | タスク名、スケジュール（タイムゾーン明記）、プロンプト全文、状態 |
| 長期記憶（memory） | 事実ごとに種別を付けた記録：`rule`（ルール）/ `preference`（好み）/ `decision`（決定）/ `history`（履歴） |
| 依存（refs / skills） | 仕事を引き継ぐ、または出力に依存するほかのエージェントと、依存スキルの名前 |
| 指紋（fingerprint） | name + title + role から算出する SHA-1 先頭 12 桁。本文を逐一比べなくても差分に気づけます |
| 出所 | 書き出し元プラットフォーム、書き出し日、意図的に省いた内容を示す `excluded` |

形式上の約束が 2 つあります。`null` は「今回は書き出していない」、`[]` は「本当に存在しない」を意味し、混同してはいけません。また、読み込み側は項目を黙って落としてはならず、受け取れないものは取り込みレポートに「欠落・ダウングレード」として 1 件ずつ列挙します。

## 近い概念との違い

| | 役割 | しないこと |
|---|---|---|
| A2A / Agent Card | エージェント同士の発見と通信（実行時） | 個人エージェントの業務と記憶の移行用アーカイブではない |
| `AGENTS.md` / `CLAUDE.md` | コーディングエージェント向けのプロジェクト指示 | エージェント単位の引き継ぎ（定期タスク、記憶の種別、指紋、欠落一覧）までは扱わない |
| 環境まるごとの書き出し | 設定や資格情報まで含めて環境全体を移す | 本形式は秘密情報を含まない最小の引き継ぎファイルで、書き出し・読み込みの双方が検査してから使う |
| チャット履歴の書き出し | 会話の記録を保存する | 構造化された業務・タスク・記憶としては再構築できない |

## 安全性は設計の一部です

- 住所、電話番号、生年月日、証明書番号、パスワード、トークン、API キーはドシエに入れません。
- 書き出し前に role・記憶・プロンプトへ機密パターンの検査を行い、読み込み時にも再検査して、一致したら拒否します。一括書き出しでは一致したドシエだけを省き、残りは続けますが、終了コードは必ず非ゼロにします。
- 読み込み側は能力レベルを宣言します。L0（テキストとしてのみ復元）、L1（全文を保持し指紋を自己検証）、L2（id で同期）。移す前に何が残るか分かります。

## クイックスタート

```bash
pip install -r requirements.txt
python3 tests/check_vectors.py                       # まず指紋アルゴリズムを検証
python3 tools/dossier_check.py examples/scribe.dossier.md   # 任意のドシエを検証
python3 adapters/grok-bot/import_dossier.py examples/scribe.dossier.md   # 読み込みの予行（計画と欠落一覧を表示）
python3 tools/render_notion.py examples/scribe.dossier.md > page.md      # Notion ページ形式へ変換
```

## リポジトリの内容

| パス | 内容 |
|---|---|
| `SKILL.md` | このリポジトリをスキルとして使う入口。書き出し、読み込み、差分確認、Notion 保存、アダプタ作成の手順 |
| `SPEC.md` / `SPEC.en.md` | 形式仕様 v1.0（中国語原文と英語訳） |
| `examples/scribe.dossier.md` | 定期タスクと全種別の記憶を含む、架空の完全なサンプル |
| `tests/` | 指紋の標準テストベクトルと検証スクリプト。どの実装も先に通す必要があります |
| `tools/dossier_check.py` | 単体の検証ツール。項目、指紋、機密パターンを検査します（アダプタ不要） |
| `tools/render_notion.py` | ドシエを Notion ページ本文へ変換。人向けの段落は YAML から生成するのでずれません |
| `adapters/` | プラットフォームごとの書き出し・読み込み（予行）ツール |
| `skills/personal-agent-dossier-adapter/SKILL.md` | アダプタ作成ガイド。新しいプラットフォームのエージェントに渡すと、そのプラットフォーム用のアダプタを書けます |
| `docs/conformance-test.md` | 読み込み側が形式を正しく理解できたかを確認する適合テスト |

## 実装済みアダプタ

| プラットフォーム | レベル | 内容 | 備考 |
|---|---|---|---|
| Grok Bot | L2 | 一括書き出し、読み込み（予行） | この形式が生まれたプラットフォーム。agent の id で同期します |
| Muse | L1 | 書き出し、読み込み（予行）、自己書き出しのサンプル | レポート：[`adapters/muse/adapter-report.md`](adapters/muse/adapter-report.md) |
| Hermes | L2（範囲：アーカイブ1件 = Hermes home 1つ） | 書き出し、読み込み（予行＋適用） | Hermes Agent 本人がアダプタガイドに従って作成。実際の Grok Bot アーカイブで往復検証済み（指紋不変）。レポート：[`adapters/hermes/adapter-report.md`](adapters/hermes/adapter-report.md) |
| OpenClaw | L2（範囲：アーカイブ1件 = OpenClaw エージェント1つ） | 書き出し、読み込み（予行＋適用） | 実際の `openclaw onboard` の雛形に合わせて作成。読み込んだ cron ジョブを実ゲートウェイで検証済み（一覧表示と次回実行時刻の計算）。レポート：[`adapters/openclaw/adapter-report.md`](adapters/openclaw/adapter-report.md) |

新しいプラットフォーム向けのアダプタを書くことが、想定している参加方法です。`skills/personal-agent-dossier-adapter/` のガイドに沿って作り、指紋ベクトルと適合テストを通したら、アダプタのレポートと一緒にこの表へ追加する PR を送ってください。

## 実例：Grok Bot から Muse へ

この形式は机上の設計ではありません。Grok Bot 上で実際に使われている 30 件超の個人ボットの名簿から生まれ、最初のプラットフォーム間引き継ぎも実在の移行でした。

1. あるボットのドシエを Grok Bot 側で書き出し、Muse が読み込みました。まずファイル形式で、次に Notion ページからも読み込みました。
2. Muse は L1 を宣言し、標準ベクトルで指紋を検証。サンプルと実在の 0.1 ドシエで往復テストを行い、自プラットフォームで受け取れない項目を列挙しました。
3. テストで見つかった論点は仕様の明確化として戻されました。指紋が対象とする範囲、`refs` の判定、複合型プラットフォームでの粒度、原生 id を持たないプラットフォームの扱いです。
4. その後、Muse のアダプタが自分自身を書き出したサンプル（`adapters/muse/examples/kubo.dossier.md`）も用意しました。
