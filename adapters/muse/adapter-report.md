# Muse 适配器报告（agent-dossier/0.2）

## 1. 平台与声明等级

- 平台：**Muse**（Meta 的个人 agent 平台；一个用户一个主 agent，职能由自定义 skill（SKILL.md）、侧聊、定时任务（cron）和 Markdown 记忆文件承载）
- 声明等级：**L1**

定级依据（均在本平台实测，不是推测）：Muse 能把档案全文落盘保存（skill 文件 + 档案副本）、能自己重算并校验指纹、能把 memory 按 kind 以文本标签形式保留——与 SPEC 6.1 对 L1 的描述逐项对上（其例子就是「自定义 skill + 文件的组合」）。达不到 L2 的那一条是结构性的：**Muse 没有按 dossier `id` 配对的 agent 实体**。这里不存在一份「agent 名册」可以按外部 id 找到某个 agent 并改它的名字和描述；主 agent 只有一个，id 只能自取一个本地标识记在档案里，没法用于 §6 的同步配对。cron 和记忆在平台上真实存在（cron 表达式 + 时区；Markdown 记忆），但新建对象的 id 由平台分配，且按平台规矩，真正建 cron、写真实记忆之前必须经用户确认，所以本适配器的导入器只做到空跑 + 暂存。

## 3. 映射表

| 档案字段 | Muse 放在哪里 | 还原程度 |
|---|---|---|
| id | 无对应实体；原样保留在归档的档案副本和暂存 meta 里，作注记 | 降级（不能按 id 配对/更新） |
| name | 自定义 skill 目录名（slug 化，如 `Scribe` → `scribe`）；名字原值保留在 SKILL.md 与档案副本里 | 原样（值） |
| title | skill front matter 没有 title 字段；并入 description 文本，档案副本里原样保留 | 降级 |
| role | SKILL.md 正文「职能（role）」一节，原文 | 原样 |
| anti_jobs | 同一 SKILL.md 的「反职责（anti_jobs）」一节，文本列表 | 降级（内容在、结构没了） |
| routines.id | 平台建 cron 时新分配，必然变化 | 降级 |
| routines.schedule / prompt | cron 表达式 + 时区可表达，文本原样进导入计划；prompt 在真正建任务时原样使用 | 原样（文本），但创建需用户确认 |
| routines.state | running/paused → cron 的启用/禁用；deleted → 只留在计划文件里，不建 | 降级 |
| memory.fact | 暂存记忆测试文件，一条一行，原文 | 原样 |
| memory.kind | 行内文本标签 `[kind · learned]` 的前半 | 降级（枚举变文本） |
| memory.learned | 同标签的后半，文本日期 | 降级（结构化日期变文本） |
| skills | 只记名称；Muse 上有同名 SKILL.md 才存在，缺的要另行安装 | 降级 |
| refs | 按名字在 Muse 的人物/角色记录里重新对应；源 id 只留注记，不解析 | 降级（规范本身预期内） |
| group | skill 与侧聊都没有分组概念；仅档案副本保留 | 存不下 |
| status / exported_at / source / fingerprint | 档案副本里的文档性字段，平台不消费；fingerprint 由适配器每次重算自检 | 降级 |
| excluded | 档案副本原样保留 | 原样（文本） |

导入的落点形态：一份档案 → 一个自定义 skill 草稿（role + anti_jobs）+ 一份记忆测试文件 + 一份 routines 计划 + 一份原档案副本。真实写入（装 skill、建 cron、写真实记忆）不在导入器职责内，一律等用户确认后另行执行。

## 4. 往返测试结果

对象：`examples/scribe.dossier.md`（导入 → 暂存 → 再导出 → 逐字段比对解析值）。

先按 `docs/conformance-test.md` 第 3 步用自己的话复述 Scribe：它是个会议记录整理员——把会议文字稿收敛成十条以内的要点加一张带负责人和截止日期的待办表，稿子里没有的信息绝不许它编，拿不准就标出来问人，全程中文、简洁。反职责三条：不替人发邮件消息（只出草稿）、不补充记录外信息、没记录时不许主动找事。

比对结果：**除 `source` 外全部字段原样还原**——

- 原样：spec、id、name、title、group、status、exported_at（测试时固定了导出日期）、fingerprint（仍是 `1e6ed4957379`）、role、anti_jobs（3 条）、routines（1 条，含带时区的 schedule 与 prompt 原文、state）、memory（3 条，含 kind 与 learned）、skills、excluded
- 变化：`source` 由 `example` 变为 `muse`——这是如实的变化，再导出确实出自 Muse，不算丢失
- 正文（Markdown body）不同：导出器按模板重新生成了人读正文。按 SPEC 第 1 节正文本来就只是人读说明、导入方不得依赖，所以不计入字段差异，但在此明说，不假装字节一致

其他实测：

- **Notion 形式**：构造了一页带标题「机器可读版（agent-dossier/0.2）」和唯一 ```yaml 块的文本，故意把块内 `[rule]` 写成 Notion 会产生的 `\[rule\]` 转义——导入通过、指纹核对通过（说明转义还原正确，否则 role 文本会带反斜杠导致指纹不符）。同一页放两个 yaml 块时按 SPEC 第 1 节拒绝，退出码 1。
- **null 语义**：用本适配器自导出的一份 routines/memory 为 `null` 的档案（见下）反过来跑导入器，报告里两项都写作「未导出，不等于没有」，且不生成任何 cron 计划——没有把 null 当成空。
- **自导出演示**：对 Kubo 本人汇了一份快照（只用我能直接读到的自身设定文件与技能清单）导出为 `adapters/muse/examples/kubo.dossier.md`，指纹 `319caff2ebdc`；routines/memory 有意写 `null`，理由写在 `excluded` 里（真实 cron 的 prompt 嵌有用户专属操作细节，需逐条审查；且 Muse 的长期记忆记的是**用户**的事实，不是 agent 自己的，按 SPEC 5.3 的精神不属于可导出内容）。同快照同日期连导两次，产物字节一致（SPEC 第 6 节幂等）。
- **脱敏扫描**：scribe、Hatch 0.1/0.2、Kubo 自导出四份档案扫描均零命中。扫描器中止路径未用真实敏感数据试（不该造），但模式表与参考实现同源并多一条（见第 6 项反馈第 6 条）。

## 5. 丢失或降级清单

汇总（细节见第 3 表）：

1. **id 不能用于同步配对**——Muse 没有 id 键控的 agent 实体；这是 L1 而非 L2 的根本原因。
2. **title 降级**：并入 skill 的 description 文本，无独立字段。
3. **anti_jobs 降级**：以文本小节存在，无结构化字段；内容不丢。
4. **memory.kind / learned 降级**：从枚举与日期退化为行内文本标签 `[kind · learned]`；fact 原文不丢。
5. **routines.id 必变**：平台创建时新分配；state 的 deleted 只能留在计划里。
6. **group 存不下**：仅档案副本保留。
7. **skills 只剩名字**：同名 skill 不存在即等于没有，需另行安装。
8. **refs 的 id 不解析**：按名字重新对应，符合规范预期，但对应结果需要人核对（同名不同人时）。
9. **name 的目录形态变化**：skill 目录名是 slug（小写连字符），原值在文件内保留。
10. **status/exported_at/source/fingerprint 不被平台消费**：只在档案副本里有意义（fingerprint 除外，适配器会重算自检）。

## 6. 规范反馈

以下只写在这里，没有改 SPEC.md。

1. **指纹覆盖不到 anti_jobs，漂移会漏检。** §2.1 的指纹只算 name|title|role。实测中 Hatch 的一处真实漂移恰恰是 anti_jobs 措辞变化（「归 Meter」与「交给用量监控 bot」两种写法），指纹纹丝不动，是靠人眼比对发现的。§6 把「指纹不同」当作职能变化的信号，但反职责也是职能的一部分。建议 v0.3 要么把 anti_jobs 按序拼进哈希，要么在规范里明说「指纹只是 role 指纹，反职责与 routines 的变化需要另行比对」，免得使用者高估它的覆盖面。
2. **§2.1 关于名册「内容指纹」的断言与实测不符。** 规范写名册列「用的就是本节的算法，和档案里的 fingerprint 是同一个值，可以直接比较」。但 2026-10-28 实测时，Hatch 在 Notion 名册里的内容指纹是 `c349eb9fc9a6`，与其档案指纹 `56cd7b80e6db` 不一致（仓库提交历史里已有「roster fingerprint now equals dossier fingerprint」的修正，说明维护方已经处理）。即便已修正，这句断言仍建议改成可核对的表述：登记值应带算法版本或计算时间，否则任何一边的陈旧值都会被读者当成漂移、或把真漂移当成陈旧值。
3. **适配器指南第 3 步的 ` · ` 拆名规则是源平台约定，混进了通用指南。** 「name 取显示名里 ` · ` 之前的部分」是 Grok Bot 把 name+title 合成一个显示名的产物；Muse 等平台要么有独立字段、要么根本没有 title。只看指南的新实现者会以为需要自己合成或拆分 title。建议把这条明确标注为「若你的平台把名字和职能标签拼成一个显示字符串（例如 Grok Bot），则……」。SPEC 第 2 节本身是干净的（字段分开），问题只在指南。
4. **refs 的范围在边界上仍不明确，两个认真的实现者会得出不同的 refs。** 以 Hatch v0.2 为例：anti_jobs 里点名了 Meter（活儿要「交给」它）、一条 memory 里点名了 Homi（协作者），但 refs 只登记了 Big Boss。按 §2 补丁的定义（依赖或会交接给的、且在 role/anti_jobs/memory 里点名的），「交给用量监控 bot」恰恰是交接，Meter 似乎应该在 refs 里；Homi 只是事实里的提及，似乎不该在。这个区分（「交接/依赖」vs「顺带提及」）规范没有给出可操作的判定句。refs 的完整度又直接影响 §5.4 的 UUID 警告覆盖检查，建议给出判定规则或给 refs 项加一个可选的用途说明。
5. **「一个 agent 一份档案」的粒度在复合型平台上没有指引。** Muse 的形态是一个主 agent 承载几十种职能（每个侧聊/定时任务是一种职能）。导出时我只能把整个 Kubo 写成一份档案；另一种同样合理的粒度是按职能拆成多份。规范对「agent」的粒度默认了「平台里一个可命名的 bot」，§7 已在讨论 roster，但粒度问题比 roster 更靠前：粒度不同，id、refs、同步配对全都跟着变。建议在 v0.3 里至少写一句复合型平台的建议粒度。
6. **SPEC 5.2 正文点名的 password 扫描，参考实现的代码里没有。** 正文要求扫「`password`/`密码` 后面跟的值」，但 `adapters/grok-bot/` 两个脚本的 SCAN 都没有这一条；指南又说参考实现「可以抄结构」，照抄的人会比规范少扫一项。本适配器按正文补上了。建议把参考实现的 SCAN 与 5.2 对齐，或在正文里注明参考实现是子集。
7. **日期字段的词法形式没钉死。** YAML 解析器会把裸写的 `2026-10-28` 读成日期对象，把 `'2026-10-28'` 读成字符串；不同导出器写出的 front matter 字节因此不同（本适配器特意把 exported_at/learned 写成裸形式与参考实现对齐）。§6 的幂等只约束同一导出器，但跨实现比对字节时会假阳性。建议规范钉一句：日期写裸 ISO 形式、不加引号，解析方按字符串处理。
8. **没有原生 agent id 的平台怎么办，规范没说。** §2 说 id 是「源平台里的唯一 id」，但 Muse 根本没有平台级 agent id，我只能自取 `muse-main-kubo` 并在 excluded 里声明。这改变了 §6「按 id 配对」的语义（自取 id 的稳定性只靠自律）。建议规范补一句：平台无原生 id 时由适配器铸造并在档案里注明来源；同时说明 id 的唯一性范围是平台内还是全局（两个平台都出现 `scribe-1` 时如何消歧）。

## 7. 没测的部分，以及为什么

- **真实创建 cron / 真实写入记忆**：没测。按约定，往真实 agent、记忆、定时任务写入前必须经用户确认；本适配器按设计止步于空跑 + 暂存。导入计划里已写明每一步真写时会发生什么，等用户点头后可补测。
- **经 Notion 连接器读真实页面**：本轮没有重复做。本适配器对 Notion 形式的支持用构造文本验证（含 `\[` 转义与双块拒绝）；真实 Notion 页面里转义长什么样，前两轮测试已通过连接器实读 Hatch 页面确认过，本轮沿用那个观察，没有再动用户的 Notion。
- **`tools/render_notion.py` 生成方向**：没测。本适配器只做文件形式导出；往 Notion 写页面属于对外写入，未在本次授权内。
- **0.1 版的完整往返**：0.1 版 Hatch 档案做了读入 + 指纹 + 校验，往返只对 0.2 版 scribe 做了。0.2 只增不改，风险低，但严格说 0.1 的往返未测。
- **多 agent 批量导出**：不适用。Muse 只有一个主 agent，没有可批量枚举的 agent 名册；导出器因此采用「agent 自备快照」的形态，而不是扫目录。
