> 换平台时，把一个个人 AI agent 的「工作」完整地带走。

![冷启动测试：全新 Hermes 只靠一句话接住另一个平台的 agent](docs/images/cold-start-hermes.png)

*一个刚装好的 Hermes，没给它任务书，只说了一句话，它就自己把另一个平台的 agent 搬了过来。搬完再导回去，指纹和原来一模一样。这件事的完整经过在后面的案例里。*

## 快速开始

这个仓库只做一件事：把一个个人 AI agent 的工作打包成一个文件，换平台时整份带走，不丢东西。下面是三种最常见的情况，你是哪种，就看哪一段。

### 把你的 agent 搬到新平台（不用命令行）

```bash
git clone https://github.com/AidaShika/personal-agent-dossier
```

把上面克隆下来的仓库交给你的 agent，当作一个 skill 给它（skill 可以理解成给 agent 的一份操作手册；或者直接让它读仓库里的 `SKILL.md`）。然后用平常说话的方式吩咐它一句：「把你的工作全都打包成一个文件，我要把你搬到另一个平台了。」到了新平台，再对那边的 agent 说：「这个文件里是你之前的工作，接过来吧。」

它交回来的那个文件，就是这个项目说的「档案」（英文 dossier）。导入的时候不会马上写死：会先试跑一遍（行话叫 dry-run，就是空跑一次，什么都不改），把打算怎么做、哪些东西可能丢、丢在哪儿，全列出来给你看，你点头了才真的写。最后你会拿到一份 `.dossier.md`，agent 还会报一个「指纹」给你。指纹是从文件内容算出来的一串短码，两个平台算出来的一样，就说明搬过去的内容没走样。

### 验一验别人给你的文件（一分钟）

```bash
pip install -r requirements.txt
python3 tools/dossier_check.py 路径/任意.dossier.md
```

跑完，检查器会告诉你三件事：这份文件的栏目齐不齐；它重新算出的指纹，和文件里写的是不是同一个；里面有没有不小心夹带敏感信息。手头还没有自己的文件？先拿仓库里现成的 `examples/scribe.dossier.md` 试一遍，那是一个编出来的 agent，专门给人练手用的。

### 给你的平台搭桥

```bash
python3 tests/check_vectors.py   # 指纹算法必须在 8 条测试用例上全部对齐
```

「搭桥」的意思是：你的平台如果还没有现成的导入导出工具，就照着指南给它写一个，这个工具就叫适配器。适配器说白了就是一段替某个平台做导入导出的代码，像插座上的转换头。先跑上面的命令，确认你算指纹的方法和标准答案（测试向量）完全一致；再照 `skills/personal-agent-dossier-adapter/` 里的指南把适配器写出来；最后跑一遍 `docs/conformance-test.md` 里的一致性测试。全部通过的标准是：8 条用例全对，而且把一份档案导出去、再导回来，指纹还是原来那个。


## 要解决的问题

这套东西是我自己搬家搬出来的。这两个来月我一直在 Grok Bot 上跑一批个人 agent，它们烧的是我 X Premium 的额度，agent 一多，额度完全不够用。正好 Muse 在日本上线了，我想把 Grok Bot 的 agent 搬过来，可一只一只手搬，实在太麻烦。

一个 agent 用上一段时间，早就不是一段提示词了。它有自己的工作职责，也有一份「明确不做哪些事」的清单；它有定时要做的任务，记得住长期记忆，还要跟其他 agent 配合、用好几个 skill。这些东西都存在旧平台里面。换平台的时候靠手工复制，很容易悄悄丢东西：定时任务的时间抄过去了，完整的 prompt（给 agent 的指令原文）却没跟上；记忆搬过去了，却变成没分类的一大堆；最麻烦的是，到底丢了什么，当场谁也说不清，常常要等 agent 开始做错事，才发现是搬家时落下的。

**personal-agent-dossier** 就是把这场交接写成一个文件：文件开头是一小段机器能读、也能核对的结构化信息（YAML front matter），后面是给人读的正文（Markdown），同一份内容还能存成一个 Notion 页面。这个仓库本身就是一个 skill：agent 把仓库克隆下来，照着 `SKILL.md` 里写的路线走，就能自己把档案导出或导入。

## 一份档案里有什么

一份档案分六个部分：

| 部分 | 内容 |
|---|---|
| 职能 | 它负责做什么的全文（一个字不改地保留），外加「明确不做的事」 |
| 定时任务 | 任务名、什么时候跑（写明时区）、任务的完整说明、现在的状态 |
| 长期记忆 | 一条条记住的事实，每条都标了类型：`rule`（规则）/ `preference`（偏好）/ `decision`（决定）/ `history`（发生过的事） |
| 依赖 | 它要把工作交给谁、又依赖谁（`refs`），还有它要用到的 skill 名字 |
| 指纹 | 用 name、title、role 三样算出来的一串 12 位短码（SHA-1）。两个平台不用把原文逐句对一遍，比一下指纹，就知道内容变没变 |
| 出处 | 这份档案是从哪个平台、哪天导出的；还有一份 `excluded` 说明，写清这次有意没带哪些东西 |

有两条规矩必须守住。第一条，`null` 和 `[]` 不能混着用：`null` 的意思是「这次没有导出这一项」，`[]` 的意思是「这一项本来就没有」。第二条，导入的一方不许偷偷丢东西：新平台实在放不下的字段，要一项一项写进导入报告里，放在「丢失或降级」清单下面，明明白白告诉你。

## 和相邻概念的区别

下面这几个词都和 agent 有关，但干的不是一回事：

| | 它做什么 | 它不做什么 |
|---|---|---|
| A2A / Agent Card | 让 agent 之间互相找到对方、互发消息（运行时通信） | 不管把一个 agent 的工作和记忆打包搬家这种事 |
| `AGENTS.md` / `CLAUDE.md` | 写给编程 agent 的项目说明文件 | 不是为「交接一个 agent」设计的：没有定时任务、没有记忆分类、没有指纹，也没有丢失清单 |
| 整机状态导出 | 把整个安装连同配置、账号凭据一起搬走 | 我们这个格式只带交接真正用得上的那一份最小内容，不放任何秘密信息；而且导出、导入之前都要先扫一遍敏感信息 |
| 聊天记录导出 | 把聊天流水存下来 | 只有流水，重建不出有条理的工作职责、任务和记忆 |

## 安全是设计的一部分

- 住址、电话、生日、证件号、密码、令牌、API key，这些永远不写进档案。
- 导出之前，先把职能、记忆和任务说明拿敏感信息扫描过一遍；导入的时候再扫一遍，扫到就拒绝导入。一批一起导出时，如果只有某一份扫出问题，就跳过那一份，其余照常导出，但整批要以非零退出码收尾，不许装作什么都没发生。
- 导入的一方要先讲清自己能做到什么程度：L0 只能把内容还原成文字；L1 能把全文存下来，还能自己核对指纹；L2 能按每个 agent 的 id 持续同步。这样在动手之前，你就知道哪些东西能留住、哪些留不住。

## 内容

| 路径 | 说明 |
|---|---|
| `SKILL.md` | 这个仓库当 skill 用时的入口：导出、导入、核对两份档案差在哪、存到 Notion、写适配器，几条路线都在这里 |
| `SPEC.md` / `SPEC.en.md` | 格式的正式规范 v1.0（中文是原版，英文是译版） |
| `examples/scribe.dossier.md` | 一份编出来的完整示例，定时任务和各种记忆类型都有 |
| `tests/` | 指纹算法的标准答案（测试向量，就是一组提前算好正确答案的用例）和检查脚本；哪家来做实现，都先得过这一关 |
| `tools/dossier_check.py` | 单独就能用的检查工具：查栏目、查指纹、查敏感信息，用不着先装任何平台的适配器 |
| `tools/render_notion.py` | 把一份档案变成 Notion 页面的正文；给人看的那几段是直接从档案数据生成的，不会和档案本身写得不一样 |
| `adapters/` | 各个平台的导出工具和导入工具（导入默认先试跑） |
| `skills/personal-agent-dossier-adapter/SKILL.md` | 写适配器的指南：把这份指南交给新平台上的 agent，它能自己把那个平台的适配器写出来 |
| `docs/conformance-test.md` | 给导入方的一套测试，跑过它，才能说明这个平台是真的把格式读懂了 |

## 已实现的适配器

| 平台 | 等级 | 内容 | 说明 |
|---|---|---|---|
| Grok Bot | L2 | 批量导出器、导入器（先试跑） | 这个格式最初就是在 Grok Bot 上长出来的；同步时按每个 agent 的 id 对上号 |
| Muse | L1 | 导出器、导入器（先试跑）、把自己导出的一份示例 | 报告：[`adapters/muse/adapter-report.md`](adapters/muse/adapter-report.md) |
| Hermes | L2（范围：一份档案对应一个 Hermes home） | 导出器、导入器（先试跑，也能真导入） | 这份适配器是 Hermes Agent 照着上面的指南自己写的。拿一份真的 Grok Bot 档案完整试过：导进去、再导出来，指纹没变。报告：[`adapters/hermes/adapter-report.md`](adapters/hermes/adapter-report.md) |
| OpenClaw | L2（范围：一份档案对应一个 OpenClaw agent） | 导出器、导入器（先试跑，也能真导入） | 这份适配器是 OpenClaw 自己写的，也是拿真档案完整试过、指纹没变。写的过程中它还顺手发现一件事：OpenClaw 现在把定时任务存在 SQLite 里，不再是旧版的 JSON 文件。报告：[`adapters/openclaw/adapter-report.md`](adapters/openclaw/adapter-report.md) |

想参加进来，最实在的办法就是给你的平台写一个适配器：照着 `skills/personal-agent-dossier-adapter/` 里的指南做，让 8 条指纹测试用例全过，再跑一遍一致性测试，然后提一个 PR，把你的平台加进上面这张表，适配器报告也一起附上。

## 真实案例：从 Grok Bot 到 Muse

这个格式不是关起门来在桌上想出来的。它是从 Grok Bot 平台上的一份名册长出来的，那份名册里有 30 多个每天都在用的个人 bot。它第一次真的跨平台交接，过程是这样的：

1. 先把一个 bot 的档案从 Grok Bot 导出，交给 Muse 导入。前后导了两次：一次是直接给文件，一次是先存成 Notion 页面、再从页面导入。
2. Muse 先声明自己只能做到 L1；然后拿标准答案核对自己算指纹的方法对不对；再拿示例档案和一份真的 0.1 老档案做往返试验：导进去、再导出来，看变没变；最后把自己平台上实在放不下、只能打折接收的字段，一项一项列成清单。
3. 试验中发现的问题，后来都补回了规范里，写成明确的条款：指纹到底管哪些内容、不管哪些；`refs`（依赖关系）怎么判定才算数；一个平台上有好几个 agent 挤在一起时，按多大的单位算一份档案；碰上根本没有 id 的平台，又该怎么办。
4. 后来，Muse 的适配器把自己也导出成了一份示例档案，就是 `adapters/muse/examples/kubo.dossier.md`。

![一次导出整个名册](docs/images/export-roster-scale.png)

*先看导出这一侧。Grok Bot 的参考导出器跑一轮，把整个名册的 bot 挨个导出。哪个 bot 的档案没过敏感信息扫描，就把哪个拦下来，还要显眼地报出来。它不会不声不响地丢掉。*

![Hatch 的档案渲染成的 Notion 页面](docs/images/hatch-notion-page.png)

## 状态与路线图

现在是 v1.0。就是在这一版，项目从 agent-dossier 改名叫 personal-agent-dossier。手里还有旧档案的不用担心：导入工具照样认 `agent-dossier/0.1` 和 `agent-dossier/0.2` 这两个旧名字，指纹的算法一点没变。

还有几个问题没想定，欢迎来一起讨论：要不要把职能里提到的 bot 名单单独拆出来放一个栏目；长期记忆要不要分层、要不要设过期时间；几个 agent 之间交接工作时，关系该怎么记下来；还有附件和工具权限该怎么表示。
